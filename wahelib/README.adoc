== Message ownership

Messages returned by exported module callbacks are borrowed. WAHE never frees these original return messages, whether they come from a registered command, command processor or execution chain. The producing module manages their storage and must keep the message and any referenced payloads valid until consumers have finished with them. A non-null return pointer does not imply a heap allocation; static, thread-local and reusable module-owned buffers are supported. Returned messages must not use the host-created input allocation, which WAHE frees after the callback returns.

Ordinary textual replies returned to a module by `wahe_run_command()` are different: WAHE allocates the reply, or a copy of the responding module's borrowed message, through the calling module's allocator. The caller owns that allocation and must free it with its own allocator. WAHE continues to free temporary input copies and failed transfer allocations that it creates. Referenced audio/image/data buffers retain their separate ownership and lifetime; native recipients can access them directly without copying the payload.

In short:

* Callback input: borrow it during the call; do not free it or keep a pointer into it.
* Callback return: the producing module owns it; wahelib does not free it.
* `wahe_run_command()` text reply: the calling module owns the copy; consume it and call its own `free()` exactly once. `free(NULL)` is fine.
* Referenced payload: follow the payload's separate lifetime. Freeing the message does not normally free the image, audio or file data it describes. If wahelib packs a payload into the caller's response allocation, consume that payload before freeing the response and do not free the interior payload pointer separately.

These rules are the same for native, Wasmtime, WAMR and transpiled modules. Host-memory access avoids unnecessary payload copies; it does not make allocators interchangeable. A module's exported `module_malloc()`, `module_realloc()` and `module_free()` must use the same allocator as the module's own allocation functions.

=== Asking another module for a value

The command reply is a new allocation belonging to the caller, even if the provider originally returned a static string. Read it before freeing it:

[source,c]
----
double read_host_time(void)
{
    // Parse the owned reply before releasing it with this module's allocator
    double seconds = NAN;
    char *reply = wahe_run_command("Get raw time");
    if (reply)
        sscanf(reply, "Raw time %lg seconds", &seconds);
    free(reply);
    return seconds;
}
----

If the reply is not needed, release it directly: `free(wahe_run_command("Mouse grab"));`. Do not assume a normally silent command can never return an allocated error message.

=== Handling a command

The handler does not free the input; wahelib frees its temporary input copy after the call. A string literal is a valid borrowed result and must not be freed:

[source,c]
----
EXPORT("module_message_input")
char *module_message_input(char *message)
{
    // Inspect the borrowed input without freeing or retaining it
    if (message && strcmp(message, "Get status") == 0)
        return "Ready";
    return NULL;
}
----

If the handler needs to remember an input value, allocate and retain its own copy of that value; release the saved copy on replacement or `Deinit`. Never return a stack-local array or a pointer into the borrowed input. A static or thread-local result buffer must remain valid until consumption is complete; callers must not keep it across calls that can overwrite it. Modules used concurrently must protect result storage or provide independent storage per invocation/thread.

=== Forwarding a command from a command processor

`module_proc_cmd()` also returns a borrowed result. A processor forwarding an owned `wahe_run_command()` reply must manage that allocation itself. This simple example assumes serialized, non-reentrant calls:

[source,c]
----
static char *processor_reply;

EXPORT("module_proc_cmd")
char *module_proc_cmd(char *command)
{
    // Replace the previous module-owned result after its consumer has finished
    free(processor_reply);
    processor_reply = wahe_run_command(command);
    return processor_reply;
}
----

Release and clear `processor_reply` during `Deinit` as well. Do not free it immediately before returning it, and do not rely on wahelib to free it afterward. Framebuffer and audio descriptors may similarly use reusable module-owned text and payload buffers as long as their lifetimes cover consumption.

`Init memory` is a special low-level command: its result is a virtual-memory base address, not an allocated text reply. Do not apply the text-reply `free()` rule to that address. Similarly, `Load raw file` returns an owned text descriptor describing a separate data allocation; the caller must manage both allocations according to their respective lifetimes.

The ownership regression test can be run with `bash tests/run_message_ownership.sh`. It checks borrowed callback results, caller-owned command copies, temporary-input cleanup, different module allocators, command processors and execution chains. On Windows, an optional miniaudio DLL path also checks a real borrowed native response without starting an audio device or opening a window.

== Selecting a WebAssembly runtime

Define `WAHE_WASMTIME` to build the Wasmtime backend or `WAHE_WAMR` to build the WAMR backend. The two definitions are mutually exclusive. A WAMR build must make `wasm_export.h` available and link the WAMR runtime library.

`Shrink memory to N bytes` uses this fork's allocator-coordinated Wasmtime APIs when built with headers defining `WASMTIME_MEMORY_SHRINK_COORDINATED`. WAHE opts the engine into explicit bounds checks and applies requests synchronously while CIT Alloc still holds its allocator lock. Shared memories immediately publish the smaller logical size and mark their retained backing for later reclamation; ordinary memories shrink and decommit synchronously. Targets are rounded up to Wasm pages and clamped to the module's declared initial minimum. Runtime import minimums are also enforced. Growth zeroes reused bytes and prevents stale reclamation of regrown pages.

The guest allocator and all host users must have relinquished the entire removed tail, including allocations, runner stacks, TLS, pending memory operations, references and atomic waiters. Other runners may keep using the retained prefix. Holding the allocator lock excludes reallocation but does not automatically exclude host users. The runtime cannot invalidate previously checked bounds in running code. This is an explicit cooperative contract, not safe shrinking of arbitrary live memory. Explicit bounds checks can reduce memory-access performance.

The host calls `wahe_reclaim_module_memory(ctx)` at an explicitly established safe point to release pending shared-memory backing. Before calling, prevent new runner execution, wait for existing calls and pending memory operations to finish, exclude runner creation/destruction and host memory accesses, and release any references/slices spanning the unused tail. Keep those exclusions in place until the function returns. The function does not stop runners or track retained host pointers; a Wasm return or the end of one execution chain alone does not establish this safe point. There is no automatic reclamation from callbacks, function returns or the audio thread. Hosts that never establish a safe point retain the backing, although the logical size still shrinks immediately.

`wahe_reclaim_module_memory` returns `1` when reclamation succeeds or no work is pending, and `0` on failure. Failed work stays pending for a later retry. Reclamation uses the runtime's current logical extent, not the original shrink target, so intervening growth is preserved and the logical size is unchanged. Older Wasmtime, WAMR and native-only builds accept the maintenance call as a successful no-op.

Requests are never queued across further guest allocations: an unchanged page count does not prove the tail remains unused. With older Wasmtime headers, guest callback requests are ignored; the optional checked extension can still service ordinary-memory requests made with no live Wasm calls. WAMR continues to ignore the command. `WAHE_WASMTIME_HAS_MEMORY_SHRINK` controls only this older checked-extension fallback.

The WAMR backend uses the runtime embedding API, raw native imports, shared-memory child instances, independent globals and LLVM TLS initialization. To provide WAHE's runner and dynamic-thread behavior, build WAMR with thread manager, shared memory and WASI threads enabled. `WAMR_BUILD_LIB_WASI_THREADS=1` enables WAMR's heap-backed auxiliary stacks. Enable `WAMR_BUILD_MEMORY64=1` when loading wasm64 modules. A representative interpreter build also enables `WAMR_BUILD_INTERP=1`, `WAMR_BUILD_FAST_INTERP=0`, `WAMR_BUILD_LIBC_BUILTIN=1`, `WAMR_BUILD_LIBC_WASI=1`, and `WAMR_BUILD_INVOKE_NATIVE_GENERAL=1`.

WAMR modules must define and export their linear memory; unlike the Wasmtime backend, WAMR's public embedding API cannot supply an imported host memory. WAHE requires module memory to keep one host address, so growable WAMR memory must be bounded and shared. Unshared WAMR memory is accepted only when its initial and maximum page counts are equal. This restriction is necessary with WAMR 2.4.3 builds that enable Memory64, because that setting disables the Windows reservation mode and ordinary unshared `memory.grow` can move the allocation.

Multiple runners additionally require bounded shared memory, a stack-first module, and the usual exported stack pointer and TLS metadata. The stack size in `Create thread with` is a required minimum under WAMR: the child uses the module's linked auxiliary-stack size because WAMR's public child-environment API does not accept a per-child stack size. WAMR 2.4.3 only discovers auxiliary stacks for wasm32 modules, so wasm64 modules are supported with one runner but cannot use runner creation unless a WAMR version with memory64 auxiliary-stack support is selected and `WAHE_WAMR_MEMORY64_THREADS` is defined as `1`.

`WAHE_WAMR_MAX_THREADS` sets WAMR's process-wide runner limit and defaults to 64. `WAHE_WAMR_NATIVE_STACK_SIZE` sets each execution environment's native stack and defaults to 64 KiB. `WAHE_WAMR_APP_HEAP_SIZE` can override the application heap reserved for auxiliary stacks; zero selects an automatic size based on the linked Wasm stack and runner limit.

When linking a standalone Windows host with the MSYS2 UCRT64 toolchain, pass `-static` on the final compiler link command to avoid a runtime dependency on MSYS2 DLLs such as `libwinpthread-1.dll`. The resulting executable still uses Windows system and UCRT API-set DLLs. Alternatively, distribute every imported MinGW runtime DLL beside the executable.
